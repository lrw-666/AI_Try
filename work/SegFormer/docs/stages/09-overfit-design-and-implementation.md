## 1. 本阶段回答什么

## 5. AMP 跳步修复：必须区分两类异常

原训练在 attempt 76 因梯度范数 inf 中断。第一次修复允许 GradScaler 跳过后，记录运行完成了 201 次尝试中的 200 次更新：attempt 76 的 loss 有限，scale 从 65536 降至 32768，下一次恢复；保存的优化器 step 数可进一步核实是否真的只更新了 200 次。

但“loss 有限、总范数 inf”并不自动证明是可安全跳过的 AMP 溢出。各个梯度元素可能全有限，而 FP32 范数归约溢出；此时 GradScaler 未必标记异常，若照常 step，参数仍可能更新，外层却误计成跳步。

本轮将更新步骤收紧为：

```text
scaled backward → unscale_
→ 检查逐元素梯度，以及 GradScaler 缓存的 found_inf
→ 正常路径：有限范数检查后才裁剪，裁剪后梯度仍须有限
→ scaler.step，用 optimizer post-hook 观察 AdamW 是否确实执行
→ scaler.update，核对实际执行与溢出决定一致
→ 跳步路径核对所有参数与优化器 step 计数未变，scale 确实下降
→ 参数必须有限；首个成功更新的编码器/头必须有梯度和真实变化
```

范数溢出而非 scaler 确认的梯度溢出，或关闭 AMP 时梯度非有限，均在 step 前停止。连续 3 次实际跳步停止，成功更新后连续计数清零；不会把累计 3 次误当连续 3 次。首步两处 probe 只是附加证据，真实成功计数来自 optimizer 是否执行，不依赖 `scaler.step()` 返回值。

实现读取了已锁定 PyTorch 2.10 的私有 `_found_inf_per_device`；本地源码和真实 CPU GradScaler 回归已核实。以后升级 PyTorch 时必须重验该接口，不将其当作跨版本稳定 API。AMP 偶发溢出可恢复，但持续异常仍需排查，不能一概称作正常现象。

## 6. 本轮其他完善

- `evaluate_dataset` 改用实际 `dataset.split`，并在正常/异常退出都恢复调用方 train/eval 模式。旧文件中的 val 误标不再被当前代码延续。
- 原 smoke 重载虽然加载了保存的 processor，却未传给 Dataset，实际回用了原预训练目录的预处理。本轮明确注入保存 processor，并核对配置和固定预览身份。
- `_render_zoom` 原先算了 ROI，却只画全图。现上排给全图及 ROI 框，下排真正裁出 source/GT/概率/预测，色阶固定。新图来自已保存的模型，不重训八图。
- 来源记录扩展到训练入口、数据筛选、配置和几何代码；新只读复验另保存所有当前模块和测试文件 SHA。原 run 的源码缺口不伪造成已补齐。
- `run_check` 先验产物 bytes/SHA、配置/清单/快照，再严格加载模型、processor、training_state；核对全部模型张量、优化器逐参数 step、GradScaler、计数，最后实际 CUDA B1 原图计分。

历史 overfit 没保存训练结束前的完整概率图，因此新进程只能核对原有逐图混淆量/指标，**不能声称概率差为零**。该检查明确记为 not_available/null；smoke 有保存概率数组，可以做实际概率差和 XOR 对照。

## 9. 学习自测

1. 为什么 043 可以让全局 IoU 很高，而三个小缺陷仍可能很差？请用 GT 前景占比与宏平均解释。
2. 为什么有限梯度的总范数仍可能 inf？它与 GradScaler 的 found_inf 有什么区别？
3. 重载模型为何还须使用保存的 processor，而不仅是权重和网络结构？
4. “原图分数一致”与“完整概率图一致”分别能证明什么？没有旧概率图时该如何报告？
5. 更新 0 必须在任何参数更新之前，但是否必须在创建 optimizer 之前？
