### 本轮要交付什么

11 月 16 日前的目标是一套能解释问题、能说明证据边界、能回答“为什么值得做、如何做下去”的开题材料。最低工作包包括：

1. 清楚的研究对象、任务定义和拟研究问题。
2. 与问题有关的文献脉络，以及现有证据尚未回答的部分。
3. 可复现的数据划分、标签和评价协议。
4. 可信的可行性证据：优先争取一个模型闭环；若训练尚未跑通，则提交经过核验的数据流程、实际报错和资源测量，明确写成流程验证与待解决问题。
5. 一张方法图，以及开题后的实验、消融、风险和进度计划。
6. 符合学校模板的报告、PPT、答辩讲稿和离线备份。

这是一份工作底线，不是对学校正式要求的替代。是否必须已有完整实验结果、需要哪些字段和签字，以学校和导师的实际要求为准。当前不把“完成两模型完整对比”“证明方法提升”或“确定多个创新点”设为开题必过条件；没有实测结果就不填写指标，也不将预期提升写成结论。

## 5. 最小实验验收：什么才算有证据

下面是之后执行实验时的核验清单，目前均不代表已经完成。

### 数据与评价协议

- [ ] 明确任务为缺陷前景/背景二值分割，核验缺陷像素值、正常样本的全零掩码，以及图像、掩码对应关系。
- [ ] 保存原图级 train/validation/test 清单、固定随机种子、各划分正负样本数；同一原图生成的所有裁块必须留在同一划分。若能识别同一板件/拍摄组，应评估并记录同组泄漏风险。
- [ ] 使用 PCB1 high-shot 的官方训练/测试清单，从训练部分另取验证集，注明“基于官方 high-shot 的派生训练/验证规则”。若改变官方测试成员，则另行命名自定义协议，不混称原论文官方成绩。
- [ ] 使用训练集训练、验证集选择阈值和配置；测试集不参与挑模型、调阈值或根据错例反复调整方案。若目前只做验证，材料准确标注验证集结果，保留测试集用于冻结方案后的评价。
- [ ] 对图像和掩码保持同一几何变换；掩码缩放使用适合离散标签的方式。切块时保存坐标、重叠和回拼规则，计分时说明原图或裁块粒度，不能当成新增独立样本提高可信度。
- [ ] 以缺陷前景 IoU、Dice 为主，写清阈值和汇总方式。至少区分缺陷图像表现与正常图像误报；不让正常图像的高背景 IoU/像素准确率掩盖缺陷漏检。
- [ ] 写明空掩码的处理约定；正常图像单列误报图像数/比例或误报像素量，并注明预测前景的判定规则。缺陷图像的逐图统计与全数据累计前景统计不可混用名称。

### 第一模型闭环

本轮的最小闭环可以是小范围的数据读入、前向、至少一次有效参数更新、保存后在独立进程载入并推理；它不要求模型已经收敛。相应分数只能标注为短程/小样本、未验证收敛的初步结果，不能据此评价最终性能。尚未达成这一链路时，按实际完成环节记录流程验证。

- [ ] 一份固定配置能从数据读入运行到有限的 loss 和反向传播，记录实际训练范围、epoch/step、种子、输入尺寸、batch、优化器和预训练来源。
- [ ] 成功保存 checkpoint，并在重新启动的进程中加载，完成推理和计分；对应代码版本、环境说明、数据清单及命令可追溯。
- [ ] 至少有少量正常、缺陷图像的输入/真值/预测叠加图；同时保留失败样例，不能只挑最好看的图片。
- [ ] 实验卡记录实际 GPU、显存峰值、短程耗时和运行范围；只有单步或小样本验证时准确命名。单次、单种子的初步结果不支持稳健提升结论。
- [ ] 能用自己的话解释输入、模型输出、loss、阈值和 IoU/Dice 的含义；Agent 生成了代码并不等于自己已掌握或代码已正确。

### 第二模型的额外条件

- [ ] 编码器冻结状态可核验，分割 head 有梯度；patch token、空间尺寸、上采样与原图掩码保持一致。
- [ ] 继承同一数据划分和评价脚本；记录预训练权重、输入分辨率、head 和训练预算。若两模型因资源使用不同尺寸或预算，明确限制，不能据此简单归因“某架构更好”。
- [ ] 未完成以上条件时，标注“接口验证”“单步验证”或“拟做对照”，不作为已完成对比写入结论。

## 6. 风险与可执行回退

| 触发情况 | 先核对什么 | 当期回退 | 报告如何表述 |
| --- | --- | --- | --- |
| GPU 启动失败、显存溢出或环境冲突 | 实际显存、PyTorch/CUDA/驱动组合、输入尺寸、batch，以及完整报错 | batch=1、小分辨率、减少验证频次或仅做短程验证；稳定后再逐项增加。云端只在明确瓶颈、费用上限和可复现环境后考虑 | 记录实测资源与限制；不承诺某卡几小时必跑完 |
| 大图缩放后微小缺陷不可辨 | 原图与缩放后掩码的缺陷像素、叠加图和错例 | 本轮先量化缩放损失并收窄结论；有余力才选一项高分辨率或切块验证，完整研究留到开题后 | 将高分辨率/切块列为待验证策略，不预写“已解决小缺陷” |
| 裁块带来重复样本或跨集泄漏 | 原图 ID、划分清单、裁块坐标与回拼过程 | 先锁定原图划分再裁块；删去不可信的比较结果，保留可核验部分 | 说明修订了哪个协议；不沿用泄漏指标 |
| DINO 权重取得、条款、依赖或 token 形状卡住 | 官方取得方式、适用条件、特征输出接口和本地日志 | 保留 SegFormer 作为可行性证据；DINO 放入后续计划，不临时引入第三模型 | 第二独立对照未完成及其原因，避免写成融合已可行 |
| PCB1 标签量或对象边界不适合预想问题 | 实际样本统计、缺陷类型与样例，而非仅看数据集名称 | 向导师展示问题与样例，收窄开题题目；另一 PCB 类别作为后续扩展，不在临近截止铺开多套数据 | 区分数据集内结论与实际板级外观/装配适用范围 |
| 11/5 仍没有完整训练 | 一条可复现的最小失败路径与已有成功环节 | 限时排障，取消第二模型必做，完成数据协议、方法图、资源证据和后续计划 | 明确“流程验证/待完成训练”；正式开题证据要求仍需导师与学校判断 |
| 工作占用或材料反馈晚到 | 剩余主动时间与必须提交字段 | 削减模型和实验范围，优先修必须字段和明显论证问题；保留 11/14 预演、11/15 定稿 | 不补造实验进度，不用扩大题目补足页数 |

## 7. 报告建议结构

先收集学校模板并按其字段映射，以下用于在模板未拿到时开始写作，不替代正式格式。

1. **研究背景与意义**：工业视觉中具体哪类可观测缺陷需要像素级定位，为什么从 PCB 场景起步；限制好对象范围。
2. **国内外相关研究**：根据已读综述归纳有监督分割、预训练特征利用等线索；异常检测作为任务边界或备选背景，避免把所有路线平铺成同一课题。
3. **问题定义与研究目标**：输入、输出、监督信息、数据范围及目标；把拟验证的问题与尚无证据的假设写开。
4. **拟研究内容与技术路线**：SegFormer 独立基线、冻结 DINO 独立对照的目的；后续根据证据选择高分辨率、切块或融合等候选，不提前承诺最终结构。
5. **数据与实验设计**：划分与泄漏控制、标签、前景指标、正常误报、对照条件、后续消融和扩展计划。
6. **前期基础与可行性**：5 篇综述、数据检查、实际运行到哪一步、资源测量与已有图表；只陈述可核验内容。
7. **工作安排、风险与预期成果**：开题后实验、论文与复现材料的阶段目标；不自行添加小论文或多个研究点指标。
8. **参考文献**：每条引用可定位；综述用于建立脉络，具体方法与数据协议尽量回到原论文/官方材料核实。

建议边做边写：10/31 开目录，11/2 写背景，11/4 写相关工作与协议，11/7—8 写方法和计划。11/9 之后主要做完整化与修订，不从空白文档开始。

## 8. PPT 建议与预演

先以 8—12 页正文组织，再按学校给出的讲述时间删减、合并或把细节移到备份页。页数不是硬指标，也不预设一定允许 10 分钟。

| 页次建议 | 核心内容 | 讲清的一句话 |
| --- | --- | --- |
| 1 | 题目、姓名与基本信息 | 我准备研究什么对象和任务 |
| 2 | 场景、图像与掩码样例 | 为什么需要像素级缺陷定位 |
| 3 | 相关研究脉络 | 现有方法提供了什么基础 |
| 4 | 研究问题与范围 | 这次准备验证什么，当前边界在哪里 |
| 5—6 | 技术路线与方法图 | 先用独立基线和独立对照建立证据，后续再决定改进 |
| 7 | 数据与评价协议 | 如何避免泄漏并真实衡量缺陷与误报 |
| 8 | 当前可行性证据 | 已经做到了哪一步，哪些仍待验证 |
| 9 | 后续实验、进度与风险 | 接下来怎样获得回答问题所需的证据 |
| 10 | 预期成果与结束页 | 论文和实验最终计划交付什么 |

需要 8 页时合并背景/样例、方法图/路线；允许 11—12 页时再拆开证据和风险。详细网络结构、更多错例与公式可放备份页，不靠增加正文页数填充内容。

11/14 预演时至少检查：是否超时，能否解释前景 IoU 与背景分数的区别，能否说明为什么第二模型不等于双分支融合，是否把拟做内容误讲成已有结果，离线打开材料是否正常。11/15 只围绕这些问题做最后修订。

## 9. 带方案与导师讨论的四点提纲

这四点用于尽早对齐和降低返工，不设为开始数据检查、读文献或写作的许可门槛。

1. **对象与任务**：展示 PCB1 图像/掩码；希望聚焦板级外观/装配，还是更一般的单体表面缺陷？现有数据究竟支持哪些论述？初步按有监督二值分割推进是否便于形成硕士课题？
2. **开题要求**：带学校模板核对字段、题目粒度、是否有必须展示的前期实验、答辩时长和 11/16 提交细节；说明当前没有小论文指标和明确研究点数量要求，请以正式要求为准。
3. **方法与难度**：先完成 SegFormer-B0，再视证据做冻结 DINOv3-S/16 的独立对照；后续候选包含高分辨率/切块、扩展类别或融合。哪些问题值得优先研究，怎样控制工作量且保留适中挑战？
4. **可行性与边界**：展示实际环境、日志、样例和时间预算；若两模型未全部跑完，哪些可信证据最需要补充，开题后如何安排验证？计算资源是否有现成支持，确需云算力时再估价。

## 10. 人与 Agent 的分工

| 角色 | 主要工作 | 必须交回的证据 | 使用边界 |
| --- | --- | --- | --- |
| 用户 | 理解任务、选择范围、联系导师/学校、运行实验、判断材料是否符合自己的理解 | 自己能解释的数据/方法图；真实日志；导师和学校的要求记录 | 研究判断与答辩理解不能外包给生成文本 |
| 编程 Agent | 在最小范围内实现数据加载、训练/推理/评价和配置；定位具体报错 | 修改文件、启动方式、检查输出、已知限制 | 不擅自扩展模型或自动上传数据；不能把代码生成成功当成实验成功 |
| 核验 Agent | 独立核查划分泄漏、指标语义、掩码变换、冻结状态和复现记录 | 简短问题清单及对应证据位置 | 优先查影响结论的错误；只读核验与编码可分工，避免同时改同一文件 |
| 文献/写作 Agent | 提炼已读材料、整理引用、检查报告/PPT逻辑与术语一致性 | 可追溯来源、修改建议、待核实字段 | 不编造论文、结果、导师意见或创新结论；无法确认的信息保留待核实标记 |

可按“用户明确当天最小交付 → Agent 完成一项 → 用户运行并保存证据 → 核验后记状态”的顺序使用，无需每天同时启动多个 Agent。每次交接只带相关上下文：数据协议、当前配置、完整报错、已完成环节、下一步验收；避免让 Agent 反复从旧计划推断进度。

## 11. 跨端同步与定稿检查

若本地与云端/另一台机器切换，只通过 Git 同步文档、代码、配置、数据清单和环境说明。数据清单记录相对路径、划分及必要的校验信息；原始数据按官方渠道或明确的存储方案单独取得。

- 不上传 dataset、模型 weights、cache、token、密钥或带凭据的配置；核对忽略规则和待提交内容。
- 记录 Python/PyTorch/CUDA 版本、依赖、数据根目录约定、预训练来源与运行命令；资源差异单独说明。
- 每次实验记录对应代码版本、配置和划分清单；云端生成的指标、日志和样例需可带回核验。
- 不自动 push，也不因为跨端方便而把私密配置混入仓库。本工作计划本身不执行提交、推送、租云或消息发送。

11/15 定稿时检查：

- [ ] 学校要求的必填字段、签字/盖章与提交步骤已逐项核对，具体截止时点已确认。
- [ ] 报告、PPT、讲稿对研究对象、模型名称、数据协议、当前进度和后续计划的表述一致。
- [ ] 每个指标都能回到真实输出；每张图知道来源；不存在示意数值冒充实验结果。
- [ ] 文件名、页码、目录、引用、图片清晰度正常；导出的 PDF 已逐页检查。
- [ ] 本地和第二位置的报告、PPT、PDF与讲稿均实际打开过，演示不依赖网络。
- [ ] 11/16 提交动作、回执核对和个人答辩安排有明确提醒。

## 12. 后续实际记录方式

每天结束只需补四行实际记录：`今天完成了什么 / 证据在哪里 / 还卡在哪里 / 明天最小一步是什么`。状态可用“未开始、进行中、已核验、暂停”，只有满足对应验收后才写“已核验”。
